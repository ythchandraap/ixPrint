Introduction

ix.print receives PDFs from a web app over HTTP and prints them silently on a printer connected to this computer. The server is available on the local network at the configured port; access is protected by a token by default. Web apps calling the API from a browser must be listed in ix.print → Settings → API → Allowed websites; requests from other websites are rejected. A printer on another ix.print computer can also be reached by forwarding one server-to-server job over the LAN.

Typical flow

  1. Fetch the printer list (GET /list-printer) and presets (GET /presets) if needed.
  2. Send a PDF to POST /print as multipart/form-data (the first file field is used), with settings in the query string — or, for a designed preset, send JSON data to the same endpoint.
  3. Send a unique Idempotency-Key for each deliberate print. Reuse it only when retrying the exact same request.
  4. Save the job_id from the response, then poll GET /job-status every 2 seconds, stopping at a final state or after 10 minutes.

Settings precedence

Request parameters → preset (preset=… or this computer's default preset) → built-in defaults. Printer: printer in the request → printer in the preset → ix.print default printer → system default printer.

Presets and the default printer can only be changed from the ix.print window, not through the API.

Authentication

Tokens are created in the ix.print window → API tab (one token per application; tokens can be revoked at any time). Require a token is enabled by default: every endpoint except / and /docs rejects requests without a token with 401. Invalid or revoked tokens are always rejected.

Use Authorization: Bearer for new integrations. X-Api-Token is also accepted. The ?token= query form remains for compatibility, but avoid it because URLs can appear in browser history, copied links, or intermediary logs.

Authorization: Bearer fxp_…

Fill in the Token field above so the "Try it" buttons and code examples on this page use your token. The token is stored only in this browser. Do not put a token in public-page JavaScript; keep it on your web app's server where possible.

GET /presets/shared and GET /presets/shared/export always require a valid bearer token, even when Require a token is off. They do not accept X-Api-Token or a query token. Shared preset listing is separately controlled in the Presets tab and is off by default. The older /presets and /presets/export endpoints retain their existing behavior and token methods.

Share presets over LAN

In the Presets tab, turn on Share on LAN for a published preset. Its published settings, design and sample data are available to a computer with an API token. Allow listing shared presets via API is separate and defaults to off; when off, the receiver needs the exact preset name. Drafts, previous versions and defaults are never included.

List shared preset names (bearer token required):

curl -H "Authorization: Bearer fxp_…" "http://192.168.1.10:18032/presets/shared"

// 200
{"presets":[{"name":"Label Produk","has_design":true},{"name":"Struk","has_design":false}]}

Fetch one published preset, even when listing is disabled. The name is URL-encoded and the token stays in the header:

curl -H "Authorization: Bearer fxp_…" "http://192.168.1.10:18032/presets/shared/export?name=Label%20Produk"

// 200
{"format":"ixprint-presets","version":2,"exported_at":"","presets":{"Label Produk":{"paper":"A4","design":{"width_mm":60,"height_mm":40,"elements":[],"sample":{"sku":"A1"}}}}}

Both endpoints always require a valid bearer token, even when Require a token is off. They do not use query tokens or X-Api-Token for authentication. Existing GET /presets and GET /presets/export retain their original responses and authentication behavior.

Print parameters

Used by POST /print and POST /test-page. All are optional; empty values count as unset.

ParameterValuesDefaultDescription

Job status

GET /job-status and the status field in the /print response contain state:

stateMeaning
queuedWaiting in the queue. position = order, ahead = jobs ahead.
printingPrinting.
pausedHeld / queue paused.
errorThe job or printer has a problem (out of paper, jam, offline…); see message / printer_message. It may continue after the problem is fixed.
completedSpooler reports completion.
goneLeft the queue without a known result (e.g. cancelled).
failedix.print could not send the job; message explains why.

Poll every 2–3 seconds until completed, gone or failed, with a bounded timeout such as 10 minutes. completed means the spooler reports completion, not that paper was physically produced. For gone, check ix.print History and the operating-system printer queue. Older jobs remain in retained History.

Print result callback

Instead of polling /job-status, send callback_url (a query parameter on the /print upload and /test-page, or a field in the JSON body). When the job finishes, ix.print sends a JSON POST to that URL. The /print response then contains "callback": {"status": "watching"}.

{
  "event": "job.finished",
  "job_id": "…",
  "reference": "ORDER-42",
  "success": true,
  "state": "completed",
  "message": null,
  "printer": "EPSON_TM_T82",
  "preset": "struk",
  "sheets": 1,
  "time": "2026-09-22T10:15:03+07:00"
}
statesuccessMeaning
completedtrueSpooler reports completion.
sentnullSent to the printer; the spooler did not report the job status.

gonenullLeft the queue without a known outcome (e.g. cancelled).

If the printer has a problem (out of paper, jam, offline) before completion, one "event": "job.problem" is sent with "state": "error", "success": null and message; job.finished still follows. Requests rejected at the start (400/500) do not trigger a callback: the result is already in the response.

Delivery: success means your server responds with 2xx within 10 seconds; otherwise ix.print retries after 5 seconds, 30 seconds and 2 minutes. Redirects are not followed. A job may be delivered more than once, so process it idempotently using job_id + event.

Verification: every callback is signed with the token used to print. The X-IxPrint-Timestamp header (Unix seconds) and X-IxPrint-Signature: sha256=<hex> = HMAC-SHA256 over "{timestamp}.{raw body}", using the token's SHA-256 hex as the key. Reject it when the signature does not match or the timestamp is more than 5 minutes old.

// Node.js (Express: app.post(url, express.raw({ type: "application/json" }), …))
const crypto = require("crypto");
const key = crypto.createHash("sha256").update(process.env.IXPRINT_TOKEN).digest("hex");
const ts = req.get("X-IxPrint-Timestamp");
const expected = Buffer.from("sha256=" + crypto.createHmac("sha256", key).update(`${ts}.${req.body}`).digest("hex"));
const given = Buffer.from(req.get("X-IxPrint-Signature") || "");
const ok = Math.abs(Date.now() / 1000 - Number(ts)) < 300 &&
  given.length === expected.length && crypto.timingSafeEqual(given, expected);
// PHP
$body = file_get_contents('php://input');
$ts = $_SERVER['HTTP_X_IXPRINT_TIMESTAMP'] ?? '';
$key = hash('sha256', getenv('IXPRINT_TOKEN'));
$expected = 'sha256=' . hash_hmac('sha256', $ts . '.' . $body, $key);
$ok = abs(time() - (int) $ts) < 300 && hash_equals($expected, $_SERVER['HTTP_X_IXPRINT_SIGNATURE'] ?? '');

Callbacks require a token (without one: 400). Up to 200 jobs are monitored at once; above that limit the job is still printed and the response contains "callback": {"status": "refused", …}.

Errors

Errors are returned as JSON. Preserve the HTTP status and any fields such as code or job_id when handling them:

  • 400 — invalid parameter, missing preset, missing printer, or paper size exceeds the printer limit.
  • 401 — token missing (when required), invalid or revoked.
  • 404 — printer or job not found (read endpoint).
  • 409 — idempotency conflict, or code: "outcome_unknown". For an unknown outcome, check History and the operating-system printer queue before deciding to create a new job; do not retry with a new key automatically.
  • 413 — file lebih dari 200 MB.
  • 500 — document could not be opened or the printer rejected the job.
